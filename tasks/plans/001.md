A copy of this file is the project doc `claude/task-001-plan-2026-11-16.md`; this file in the repo is the one builder agents read.

## Purpose

Two purposes. Task 1 fully reaches the first and takes a first measurement of the second.

1. **Make the tests trustworthy.** A test that passes everything is worthless, and reading it does not show that. Task 1 runs the tests against a correct scripted agent, which must pass, and against copies that each break one rule, which must fail.
2. **Check that a built agent follows the spec's rules.** Each test puts the agent in one situation from the spec, such as "booking call gets no answer", and checks the rules that apply, such as "no second booking call". Once a real agent exists, these tests are the gate it must pass.

## Terms

- **BDD test**: a test written as sentences starting with Given, When or Then. BDD stands for behaviour-driven development.
- **LLM**: a language model such as Claude. In this plan "an LLM writes X" means a Claude Code agent writes X. The plan never calls an LLM "a model".
- **Policy model**: the file `model.py` in the spec folder. It is a small Python program, written by the agent-spec skill, that states the café policy as states and steps. It is not an LLM.
- **Script**: a small Python program with fixed logic and no LLM in it. The same input always gives the same output.
- **Feature file**: a text file of BDD test sentences, one block per scenario. Example below.
- **Step function**: the Python function that runs one test sentence. The test tool pytest-bdd matches each sentence to its function.
- **World step**: one line of a scenario in `scenarios.md`, such as "hold call answers held". It says what the visitor or the booking system does.
- **Fake booking system**: a small Python stand-in for the café's real booking system. It offers the same four tools (hold a table, book the held table, release a hold, search free tables) and keeps its data in memory. A test tells it how to answer, for example "the next booking call gets no answer".
- **Test-control interface**: the one doorway through which tests reach the booking system: set up a starting situation, force an answer, read what happened. The fake booking system sits behind it now. A real system can sit behind it later without changing a test sentence.
- **Rule checker**: a Python function that reads the recorded tool calls and messages of one test and says whether one rule held.
- **Test harness**: the fake booking system, the step functions and the rule checkers together. Task 1 builds it and proves it correct.
- **Agent harness**: the code around the LLM in a real agent: its prompt, tool wiring and orchestration. Task 1 builds none for the product.
- **Agent slot**: the one place in a test where an agent plugs in. Its job: given the conversation so far, return the next action, which is a tool call or a message to the visitor. The visitor and the booking system are scripted whatever fills the slot.
- **Reference agent**: plain Python, no LLM, that fills the agent slot and follows the café policy. A **broken variant** is a copy that breaks exactly one rule.
- **Probe agent**: a throwaway real LLM agent that fills the agent slot in slice A only: one prompt holding `rules.md`, the four tools, and a plain loop of LLM calls. It is not the product agent and is deleted after slice A.
- **Mutation test**: a way to test tests. Break the thing under test on purpose and see whether a test fails. Here the broken things are the broken variants of the reference agent, one per rule.
- **Verdict**: a run reaches a verdict when every rule checker that applies can say pass or fail. A run reaches none when the agent does something the test cannot follow, for example a tool call the scenario has no answer for.

## What a feature file looks like

For scenario SC-08 of the café spec, every word below is copied from `scenarios.md` or `rules.md`:

```
Scenario: SC-08 Table held and booked
  Given The table is free
  When visitor asks for a table for 8 or fewer
  And hold call answers held
  And visitor says yes
  And booking call answers booked
  Then rule R-01 holds: Only held tables are proposed
  And rule R-03 holds: Book only after a yes to the full proposal
  And rule R-05 holds: A booking is reported with its confirmation id
  And rule R-09 holds: The visitor is told what happened
  And the conversation ends as the policy says
```

## Two ways to run a test with a real agent

A scenario fixes the order of outside events. The reference agent follows the policy model's path, so events always line up. A real agent may ask an extra question or call tools in another order, and then the fixed answers no longer match its calls.

| Mode | The real agent plays | Job |
|---|---|---|
| **From the tested moment** (the owner's idea, 2026-11-16) | one turn. The reference agent's turns up to that moment are replayed as conversation history; the real agent takes the next action; the rule checkers judge that action. | The gate: a stable pass or fail per rule, one LLM call per test. |
| **From the start** | the whole conversation | Measured and reported, not a gate. This belongs to agent eval (tasks 9, 19). |

What the first mode does not show: whether the real agent reaches that state by itself. The replayed history is also in the reference agent's words, not the real agent's.

## Risks, riskiest first

1. **Tests proven on the reference agent may not work on a real LLM agent.** Slice A measures this with the probe agent, in both modes, before any more is built.
2. **An LLM-written rule checker may check a weaker rule than the spec states.** If one builder writes both the checker and the broken variant, both can share one misreading and the variant still fails as expected. So in slice C a different builder, which has not seen the rule checkers, writes the variants from `rules.md`.
3. **The spec may not hold enough to write the Then sentences.** Low risk: a script copies them. Kept as one cheap check in slice A.

## What this task tests, and what it does not

- **The test harness is what gets tested.** The reference agent must pass every test and each broken variant must fail.
- **The fake booking system is not the thing under test.** It stands in for the outside world.
- **No product agent is tested.** The probe agent is there to test the tests, in slice A only; its pass rates are reported and decide nothing.
- **Still missing for a product agent, outside this task (tasks 9 and 19):** an LLM that plays the visitor, and a proper LLM judge of what the agent said. Slice A uses a throwaway yes/no judge for messages and the transcripts are read to check it.

## Fake now, real system later

- **Why a fake.** A test must force rare events on demand, such as a call that gets no answer. A real system cannot be told to do that. A fake is also free and fast.
- **What a fake cannot show.** It behaves as `claims.md` says the system behaves. If a claim is wrong, the fake is wrong the same way, and every test still passes.
- **When the real system exists**, whether we own it or it has a test mode like Stripe's: a second implementation of the test-control interface talks to a test copy of the real system, and the same feature files run against it. Events the real system cannot be made to produce stay on the fake.
- **Keeping the fake honest.** One small check per system claim in `claims.md` (café: C-01 to C-05) runs against both the fake and the real system. A check that passes on one and fails on the other means the claim or the fake is wrong.
- **In Task 1:** the café has no real booking system, so only the fake is built. The one rule Task 1 must keep is that no test reaches the fake except through the test-control interface.

## Design: where each test sentence comes from

| Sentence | Copied from |
|---|---|
| `Given <step>` | the scenario's first World step (the starting situation) |
| `When <step>` | every other World step, in order |
| `Then rule R-xx holds: <rule title>` | the scenario's Rules line and that rule's heading in `rules.md` |
| `Then the conversation ends as the policy says` | the end of the scenario's path through the policy model: booked or not, held or not, what the visitor was told |

- **A script writes the feature files, not an LLM.** A script cannot reword, so the sentences always equal the spec's words.
- **Drift check.** At the start of every test run the script runs again. If its output differs from the feature files on disk, the spec has changed since the tests were made, and the run stops.
- **An LLM writes the rest, per spec**: the fake booking system from `claims.md`; one step function per distinct World step (café has 20: 2 starting situations, 7 visitor steps, 11 booking-system answers); one rule checker per rule (café has 11); the reference agent; one broken variant per rule.
- **What the agent said.** Rules R-05, R-09 and R-11 depend on what the agent told the visitor. The reference agent uses the exact sentences listed in the policy model, and the check is a text match behind one function. For a real agent that function is an LLM judge.

## The skill's verify step

The skill ends with a verify step, cheapest check first. It is the same proof Task 1 gives for the café, so every spec the skill converts gets it.

1. **Script checks, no LLM.** The feature files equal the script's output (the drift check), and every test sentence has a step function.
2. **The reference agent passes every test.**
3. **Mutation test.** A separate agent that has not seen the rule checkers writes one broken variant per rule. Each must fail the Then sentence of the rule it breaks. A variant that passes every test means that rule's checker is too weak: the checker is fixed, or the case is reported as a finding.

Limits: one variant per rule shows the checker catches one way of breaking that rule, not every way. The step makes no LLM-agent runs; whether the tests work on a real agent is measured once in slice A and afterwards belongs to agent eval.

## Slices

Each slice becomes one task file with its own done-means. No slice needs a protected path: the work is a new skill folder and new tests, and it reads the agent-spec scripts without editing them. Token basis: the three manager tasks of 2026-11-15 cost 111,854 to 529,833 agent tokens each; there is no better estimate per slice.

**A. Three café scenarios, end to end, with a real-agent measurement.** SC-08 (booked), SC-12 (booking call unanswered), SC-10 (visitor withdraws). Builds the feature-file script, the fake booking system, the step functions, the rule checkers these scenarios cite, the agent slot with both run modes, the reference agent, 2 broken variants (R-03: books without a yes; R-11: sends a second booking call), and the probe agent.

Part 1, reference agent, 0 LLM calls. Pass or fail, fixed now:
1. 3 of 3 scenarios pass with the reference agent.
2. Each of the 2 variants fails the Then sentence of its own rule.
3. 0 Then sentences contain words that are neither copied from `rules.md` nor produced from the policy model's end state.

Part 2, probe agent. These 3 scenarios have 12 agent turns in all (6 tool calls, 6 messages).
4. From the tested moment: 12 turns, 3 runs each, 36 runs. Threshold, fixed now: at least 32 of 36 runs reach a verdict. Below that, this mode needs rework before slice B.
5. From the start: 3 scenarios, 3 runs each, 9 runs. Reported only: how many of 9 reach a verdict.
6. Every transcript of the 45 runs is saved. Reported, not gated: pass rate per rule, and each case where the throwaway judge and a reading of the transcript disagree.

Cost of part 2: about $2 to $4. Basis: roughly 150 LLM calls of about 3,000 input tokens each at the $4 per million input rate in `grading.json`; an estimate, not a measurement. It needs an API key where the tests run; without one the builder parks the task.

**B. All of the café.** 17 scenarios, 11 rule checkers, the drift check, both run modes. Done means: 17 of 17 pass with the reference agent; changing one World step in a copy of the spec stops the run with a drift message. **C. Broken variants by a different builder.** One per rule, written from `rules.md` and the reference agent, without opening the rule checkers. Done means: 11 of 11 variants fail the Then sentence of the rule they break. A variant that passes every test is a finding against that rule's checker, fixed in this slice.

**D. Write the skill from the café work.** `.claude/skills/agent-spec-to-pytest-bdd/`: SKILL.md, the feature-file script and drift check as assets, the café tests as its example, and the format of the findings file it sends back to agent-spec.

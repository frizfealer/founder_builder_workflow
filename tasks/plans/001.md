# Task 1 plan: BDD skill (`agent-spec-to-pytest-bdd`), café first

Rewritten 2026-11-16 after an independent review of the first draft. **Only slice A is put up for approval** (task 49). Slices B to E are an outline, planned again once A's results are in. Nothing is built yet. A copy of this file is the project doc `claude/task-001-plan-2026-11-16.md`; this file in the repo is the one builder agents read.

## Purpose

1. **Make the tests trustworthy.** A test that passes everything is worthless, and reading it does not show that. The tests run against a correct scripted agent, which must pass, and against copies that each break one rule, which must fail.
2. **Check that a built agent follows the spec's rules.** Each test puts the agent in one situation from the spec, such as "booking call gets no answer", and checks the rules that apply, such as "no second booking call". Once a real agent exists, these tests are the gate it must pass.

Slice A does the first for 3 scenarios and measures whether the second works at all.

## Terms

- **BDD test**: a test written as sentences starting with Given, When or Then. BDD stands for behaviour-driven development.
- **LLM**: a language model such as Claude. "An LLM writes X" means a Claude Code agent writes X. This plan never calls an LLM "a model".
- **Policy model**: the file `model.py` in the spec folder: a small Python program, written by the agent-spec skill, that states the café policy as states and steps. It is not an LLM.
- **Script**: a small Python program with fixed logic and no LLM in it. The same input always gives the same output.
- **Feature file**: a text file of BDD test sentences, one block per scenario. Example below.
- **Step function**: the Python function that runs one test sentence. The test tool pytest-bdd matches each sentence to its function.
- **World step**: one line of a scenario in `scenarios.md`, such as "hold call answers held". It says what the visitor or the booking system does.
- **Fake booking system**: a small working stand-in for the café's booking system, in Python, with its data in memory. It offers the four tools (hold a table, book the held table, release a hold, search free tables) and answers each call from its own state, as a real system would. A test can also force the next answer of a tool, for example "the next booking call gets no answer".
- **Test-control interface**: the one doorway through which tests reach the booking system: set up a starting situation, force an answer, read what happened. No test reaches the fake any other way.
- **Data file**: one file in the test folder holding every value a test needs that the spec does not give. See "Where values come from".
- **Rule checker**: a Python function that reads the recorded tool calls and messages of one test and says whether one rule held.
- **Message judge**: one yes/no question put to an LLM about one agent message, such as "does this message tell the visitor the table is booked and give the confirmation id?". Needed because a real agent words things freely.
- **Test harness**: the fake booking system, the step functions, the rule checkers and the message judge together.
- **Agent harness**: the code around the LLM in a real agent: its prompt, tool wiring and orchestration. This task builds none for the product.
- **Agent slot**: the one place in a test where an agent plugs in. Its job: given the conversation so far, return the next action, which is a tool call or a message to the visitor. The visitor and the booking system are scripted whatever fills the slot.
- **Reference agent**: plain Python, no LLM, that fills the agent slot and follows the café policy. A **broken variant** is a copy that breaks exactly one rule.
- **Probe agent**: a throwaway real LLM agent that fills the agent slot in slice A only: one prompt holding `rules.md`, the four tools, and a plain loop of LLM calls. It is not the product agent and is deleted after slice A.
- **Mutation test**: a way to test tests. Break the thing under test on purpose and see whether a test fails.
- **Tested moment**: one point in a scenario where it is the agent's turn. The 3 scenarios of slice A have 12 agent turns but only 7 distinct tested moments, because they share their first steps.

## What a feature file looks like

For scenario SC-08 of the café spec, every word below is copied from `scenarios.md` or `rules.md`:

```
Scenario: SC-08 Table held and booked
  Given The table is free
  When visitor asks for a table for 8 or fewer
  And hold call answers held
  And visitor says yes
  And booking call answers booked
  Then rule R-01 holds: Only held tables are proposed
  And rule R-03 holds: Book only after a yes to the full proposal
  And rule R-05 holds: A booking is reported with its confirmation id
  And rule R-09 holds: The visitor is told what happened
```

The first draft ended each scenario with "the conversation ends as the policy says". That sentence is dropped: it pinned the one route the reference agent takes, and `DECISIONS.md` says an agent may have more than one acceptable route. The rules are the test.

## Where values come from

The copied sentences are labels. They hold no date, time or name, and a party size only as "8 or fewer". A test needs real values to run. Two homes, and no change to agent-spec:

| Home | What lives there | Who writes it |
|---|---|---|
| **The spec, unchanged** | Everything that matters to a rule: limits (claim C-07: 8 allowed, 9 not), what a proposal contains (R-03), what each tool can answer (C-01 to C-05) | agent-spec, as today |
| **The data file** | Everything else: date, time, name, party sizes (the boundary values from the limit claims: 8 and 9), the confirmation id, the visitor's and the reference agent's full sentences, and the fake's argument names | the BDD builder, once per spec |

- **Each entry in the data file is labelled** "from the spec", with the claim or rule it comes from, or "free choice".
- **The data file doubles as the list of everything the builder invented.** An entry labelled free choice that turns out to be a fact about a system or an owner's decision is reported to agent-spec as a finding. agent-spec changes only when a real case shows the need.
- **Rule checkers compare which tool was called and with which values, never a name or format.** When the architecture notes later fix real argument names, a coding agent updates the fake.
- **Data variants.** A scenario that changes the outcome is already its own scenario. Limits are covered by using the boundary values as the values. Varying names and dates to test robustness belongs to agent eval.

## Two ways to run a test with a real agent

A scenario fixes the order of outside events. The reference agent follows the policy model's path, so events line up. A real agent may ask an extra question or call tools in another order.

| Mode | The real agent plays | Job |
|---|---|---|
| **From the tested moment** (the owner's idea, 2026-11-16) | one action. The reference agent's turns up to that moment are replayed as conversation history, in full sentences from the data file; the real agent takes the next action; the rule checkers judge it. | Candidate for the gate. |
| **From the start** | the whole conversation | Measured and reported, not a gate. Belongs to agent eval (tasks 9, 19). |

Limits of the first mode, known now:
- It does not show whether the real agent reaches that state by itself.
- It checks one action. An agent that says "let me check" and breaks the rule on its next turn passes. The second mode is what catches that.
- Of the café's 11 rules, 9 need an agent message read (only R-06 and R-07 are about tool calls alone). So gating a real agent needs the message judge: a tool-call moment costs one LLM call, a message moment two.

## Risks, riskiest first

1. **The tests may give wrong verdicts on a real LLM agent.** Reaching a verdict is not enough; the verdict must be right. Slice A gates on that (lines 4 and 5 below).
2. **The builder invents what the spec does not hold, and nothing checks it.** Handled by the labelled data file, which is read before A is accepted.
3. **A skill written from one spec and tested on the same spec proves little.** So only slice A is approved now, and the final blind run uses a Harbor Goods spec.
4. **An LLM-written rule checker may check a weaker rule than the spec states.** A different builder, which has not seen the rule checkers, writes the broken variants (slice C).

## Fake now, real system later

- **Why a fake.** A test must force rare events on demand, such as a call that gets no answer. A real system cannot be told to do that.
- **What a fake cannot show.** It behaves as `claims.md` says the system behaves. If a claim is wrong, the fake is wrong the same way.
- **Later, at the implementation stage**, a second implementation of the test-control interface talks to a test copy of the real system and the same feature files run against it. The fake keeps running beside it. Not part of this task: neither example has a real system.

## Slice A: three café scenarios, with a real-agent measurement (task 49)

Scenarios SC-08 (booked), SC-12 (booking call unanswered), SC-10 (visitor withdraws). Work goes in `.claude/skills/agent-spec-to-pytest-bdd/examples/cafe/`. No protected path is touched; the agent-spec scripts are read, not edited.

Built, in this order:
1. The data file, and for each of the 7 tested moments the exact conversation history a real agent would receive.
2. The script that writes the feature files, and the drift check (the script reruns at the start of a test run and stops it when the files differ).
3. The fake booking system behind the test-control interface, the step functions, the rule checkers the 3 scenarios cite, the agent slot with both modes.
4. The reference agent and 2 broken variants: R-03 (books without a yes) and R-11 (sends a second booking call).
5. The probe agent, the message judge, and the runs of part 2.

**Part 1: reference agent, 0 LLM calls.** Pass or fail, fixed now:
1. 3 of 3 scenarios pass with the reference agent.
2. Each of the 2 variants fails the Then sentence of its own rule.
3. Every value used by a step, the fake or a replayed history comes from the data file, and every entry there is labelled. Script tests show that each "from the spec" entry cites a claim or rule that exists, that its number or quoted words appear in the cited text, and that each value fits its scenario label. The drift check covers the data file as well as the feature files.

**Part 2: probe agent.** 27 one-action runs and 9 whole conversations:
- 7 tested moments, 3 runs each, with a plain prompt: 21 runs.
- 2 deliberately bad prompts, each at the moment where it should break a rule, 3 runs each: 6 runs. "Retry any call that gets no answer" (should break R-11) and "book as soon as a table is held" (should break R-03). This is the mutation test done on a real LLM.
- 3 scenarios from the start, 3 runs each: 9 conversations.

Every transcript is saved apart from the checkers' verdicts. Claude in chat labels each of the 27 one-action transcripts pass or fail per rule before opening the verdicts. Pass or fail, fixed now:
4. The checkers agree with those labels on at least 9 of every 10 rule verdicts across the 27 runs. Every disagreement is listed.
5. For each bad prompt, at least 1 run shows the bad behaviour and is failed on its rule. If no run shows it, the prompt did not bite and is rewritten; that is not a pass.

Reported, not gated: how many of the 27 runs reach a verdict; how many of the 9 conversations reach a verdict; pass rate per rule.

Cost of part 2: about $2 to $4, capped at $5. Basis: roughly 150 LLM calls of about 3,000 input tokens each at the $4 per million input rate in `grading.json`; an estimate, not a measurement. It calls the Claude API with the owner's `ant` CLI login (`ant auth login`); no API key is stored in the repo or the environment. Only if there is no login and no key does the builder finish part 1 and park the task.

**Needs you after A:**
- Read the 3 feature files (about 25 lines) and say whether this is the test format you want.
- Bring the results to chat. Claude labels the transcripts and reads the data file.
- Then one ruling: `DECISIONS.md` describes testing a real agent as whole conversations with an LLM-played visitor and 5 trials, written for the old format. If "from the tested moment" holds up, that text needs your change.

**If A fails:** lines 1 to 3 failing means the harness design is wrong; rework A. Lines 4 or 5 failing means the tests cannot yet be trusted on a real agent; slices B to E wait and the next step is decided from the disagreements.

## Slices B to E: outline only, not approved

Slice A's result (2026-11-17): all five lines hold; 81 of 84 rule verdicts agree with the labels; cost $0.88. Two things stayed unmeasured: the probe agent never went wrong by itself, and the message judge never saw a wrong message. Task 56 tests both before slice B: a list of messages with known answers put to the judge, and 12 probe runs with a rule left out of the prompt or a pushy visitor.

- **B. All of the café.** 17 scenarios, 11 rule checkers. Every scenario gains one closing sentence, "And no other rule is broken", which runs the checkers of the rules it does not cite. A failing test quotes the rule's full text and says what the agent did. SC-17 has no World steps and its rule R-08 is cited nowhere else: either it gets a test from its rule or it becomes a finding for agent-spec.
- **C. Check the step from rule text to checker code**, cheapest first:
  1. *Clause map, by script.* Each rule is split into its clauses, each separate thing the agent must or must not do. For every clause the checker names where it is tested, or says "not checked" with a reason. A script checks every clause has an entry and lists the unchecked ones.
  2. *A fresh reader.* An agent that did not write the checkers reads each rule's text beside its checker and reports any clause the code tests more weakly than the text says, quoting both.
  3. *Mutation test, per clause.* A different builder that has not opened the rule checkers writes one broken variant per clause. A variant that passes every test means that clause's check is missing or too weak.
- **D. Write the skill** from the café work. Its verify step is: script checks (drift, data file, clause map), the reference agent passes, then the fresh reader and the mutation test of slice C.
- **E. Blind run on a different spec.** A fresh session runs the skill on a Harbor Goods new-format spec (for example `eval/agent-spec/results/switch-base-10/spec-final/`). It may read the café example; that is what an example is for.

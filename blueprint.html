Founder × Builder Workflow：Implementation Plan

用 Sunrise Café Reservation Agent 把目前已經討論清楚的「what」轉成可以真正執行、觀察、修正的「how」。這份計畫的重點不是一次把整個 framework 工程化，而是先建立最薄、最穩定的 contracts、policies 與 P0/P1 phase skills，再用真實案例驗證 routing 是否成立。

v1 原則：先定 interface，不先做 orchestrator；先做 P0/P1，不先做 P2/P3；先跑真實 feedback loop，再抽象重複 routing。
Current implementation status: shared contracts ✓ · always-on policies ✓ · /product-definition v1 frozen ✓ · /verification-design NEXT. The P0 skill has passed regression tests on Sunrise Café and a second barbershop-reschedule fixture across multiple models.

Implementation scope

1. v1 目標與非目標

v1 要證明什麼

  • Phase skill 可以只靠薄 interface 與外界互動。
  • P0 → P1 可以正常 forward。
  • P1 發現 P0 ambiguity 時，不會偷偷把 product semantics 寫進 verification artifact。
  • clear defect 可以直接 repair，不必進 Decision Management。
  • genuine uncertainty 可以正確進 Decision Management，再 commit 回 authoritative artifact。
  • upstream change 後只更新 affected downstream scope。

v1 不要證明什麼

  • 不做完整自動 /workflow orchestration。
  • 不先實作所有 P2/P3 skills。
  • 不做複雜 event bus / state machine / agent runtime。
  • 不為每個 delegated choice 建 decision record。
  • 不先設計完整 JSON schema migration / persistence framework。
成功標準不是「framework 看起來完整」；而是：不用新增 ad-hoc rules，就能讓 Sunrise Café 的 P0 ↔ P1 forward / feedback / decision / repair loop 跑通。
實驗進度： P0 已完成第一輪實證並 freeze v1。已驗證 Product Truth Admission、necessary-implication contradiction test、 ISSUE vs OMIT、atomic Issues、neutral CWO、PhaseResult contract，以及跨兩個 fixture / 多模型的一致性。 接下來的主要未知數已從「P0 能否可靠產生 Product Sense」轉成「P1 能否從 Product Sense 產生 verification design， 並在遇到 upstream gap 時正確回報 Issue」。

Shared interface

4. Shared Contracts

4.1 PhaseResult

所有 phase skill 統一回傳同一種結果。它只描述「這一輪 phase work 發生了什麼」，不替 orchestrator 做 routing decision。

phase_result:
  status: complete  # complete | blocked

  artifact_changes:  # 0..N
    - artifact: product-sense.md
      scope: confirmation
      summary: Updated confirmation semantics.

  issues:  # 0..N
    - id: I-001
      statement: <what appears wrong or unresolved>
      evidence: <what exposed the problem>
      affected_phase: P0  # P0 | P1 | P2 | P3 | unknown
      uncertainty: true
      blocks_current_phase: true

  invalidates:  # 0..N
    - artifact_or_scope: verification-design / confirmation
      reason: Confirmation semantics changed.

Collection 為空時使用空 list，例如 issues: []。

欄位用途刻意不負責
status這輪 phase work 是否能完成；只有 open Issue 的 blocks_current_phase: true 時才用 blocked。不表達 D1 verdict。
artifact_changes0..N 個本 phase 所擁有 artifact 的變更。不決定 downstream 怎麼 repair。
issues0..N 個需要 routing 的 observations；每個 Issue 都有獨立 ID。不直接決定 D2/D3/D4。
invalidates0..N 個因本次變更而已知 stale的 downstream scope；不要列 speculative impacts。不直接觸發 rerun；Lifecycle Policy 負責 routing。

4.2 Issue

An Issue reports observations only. Classification (DROP / DEFER / RESOLVE NOW), decision owner, and resolution are Decision Management output — leave them out of the Issue.

Issue:
  id: I-001
  statement: <what appears wrong or unresolved>
  evidence: <what exposed the problem>
  affected_phase: P0 | P1 | P2 | P3 | unknown
  uncertainty: true | false
  blocks_current_phase: true | false
  • id — stable identifier for this Issue within the PhaseResult。
  • statement — what appears wrong or unresolved。
  • evidence — what exposed the problem。
  • affected_phase — routing hint：根據目前 evidence，最可能需要檢查或修正這個 issue 的 lifecycle phase；不要求 root-cause proof，無法合理判斷時用 unknown。
  • uncertainty: false — 不需要新的 unresolved judgment 才能知道「什麼應該為真」；可以直接進 diagnosis / repair，不需 Decision Management。
  • uncertainty: true — current authoritative artifacts 無法導出「什麼應該為真」；使用 Decision Management。
  • blocks_current_phase — 目前 phase 是否能在不解決此 issue 的情況下誠實完成工作。

4.3 最小 ownership contract

P0 owns → Product Sense
P1 owns → Verification Design / Example Map / Eval Specs
P2 owns → Engineering Design + Build
P3 owns → Verification Evidence / Observed Learning

Rules:
No phase may silently redefine another phase's authoritative truth.
When a phase needs truth another phase owns and finds it missing or ambiguous,
it reports an Issue with affected_phase set to that phase; it does not fill the gap itself.
P3 learning is evidence, not automatically product truth.

Always-on

5. Always-on Policies

5.1 Lifecycle Policy

LIFECYCLE POLICY

1. Work only within the current phase's ownership boundary.
2. Each phase returns a PhaseResult.
3. If there is no issue, continue normally after handling any known invalidations.
4. If a clear defect is found, route repair to the earliest authoritative artifact known to be incorrect.
5. If genuine unresolved uncertainty exists, use Decision Management.
6. After an upstream truth changes, repair only known-invalidated downstream scope.
7. Rerun only affected verification.
8. Never let one phase silently redefine another phase's authoritative artifact.
9. Phase-level Current Work Objectives must be confirmed by the accountable human owner.
   Task-level objectives may be AI-derived, but must remain within the confirmed phase objective
   and must not narrow away commitments already established in authoritative artifacts.

5.2 Decision Management Policy

DECISION MANAGEMENT POLICY

When genuine unresolved uncertainty appears:

1. Do not immediately ask the human.
2. Check whether the answer is already implied.
3. Check whether existing authoritative artifacts already commit the workflow to needing an answer.
4. If required, use the Current Work Objective and commit point to determine whether it must be resolved now.
5. Classify DROP / DEFER / RESOLVE NOW.
6. For RESOLVE NOW, respect HUMAN-OWNED / DELEGATED authority.
7. Use focused investigation only when necessary.
8. D4 Wayfinder requires the D4 gate and explicit human approval.
9. Commit accepted decisions back to the authoritative artifact.
這兩份 policy 都應該很薄。完整 D1 tree、D3 investigation mechanics、D4 gate details 留在 /decision-management skill；完整 phase-specific work 留在 phase skill。

Phase skill · v1 frozen

6. P0 — /product-definition

目的

把 Product Idea + available business/domain context 收斂成 authoritative Product Sense。 v1 已用 Sunrise Café 與 barbershop reschedule 兩個 fixture 做 regression；目前 freeze，不再為單一案例持續 tuning。

Input contract

Current Work Objective
Authoritative inputs:
- Product Idea
- known business/domain context

Optional:
- existing Product Sense
- changed scope
CWO purity： Phase-level Current Work Objective 只描述這一輪要產生的 outcome / target artifact / scope； 不把 Product Truth Admission、Issue routing、Decision Management 或其他 procedure 偷塞進 objective。 例如：Produce the first authoritative Product Sense covering all eight sections using product-idea.md as the sole authoritative input.

Phase-specific work

  1. Product Framing：user / problem / desired outcome / why AI / initial boundary。
  2. Product Scope。
  3. Responsibilities & Authority。
  4. Capabilities & Behaviors。
  5. Business & Domain Rules / invariants。
  6. Failure & Recovery。
  7. Acceptable Quality。
  8. Open Questions 只保留 Founder 明確 keep-open 或 Decision Management 已分類為 DEFER 的項目。

Product Truth Admission Rule

For every candidate normative claim:

1. Explicitly established by an authoritative input?
   YES → ADMIT.

2. Necessarily implied by authoritative truth?
   Use the contradiction test:
   "If this claim were false, would authoritative truth be contradicted?"
   YES → ADMIT the minimum necessary derivation.
   NO  → it is not a necessary implication.

3. Unsupported but required to specify correctness, authority,
   or required behavior of an already-committed capability?
   YES → report an Issue.
   NO  → OMIT.

4. Never promote a claim merely because it is:
   plausible / conventional / safer / helpful / a good product choice.
Important distinction： Unsupported ≠ Issue。只有已承諾 capability 最終需要補齊的 genuine unresolved product truth 才應形成 Issue； latency、tone、future features 等未承諾細節應 OMIT，而不是全部變成 backlog。

Issue emission

When emitting Issues:
- one Issue = one independently routable unresolved problem;
- split when parts may resolve independently,
  have different owners, or receive different DM verdicts;
- do not put DROP / DEFER / RESOLVE NOW into the Issue;
- do not leak Issue IDs into Product Sense.

A genuine gap may occasionally remain visibly unresolved in Product Sense
without also being emitted as an Issue in the same run.
v1 accepts this variance provided:
1. no unsupported truth is invented;
2. the unresolved gap remains visible;
3. downstream phases must raise an upstream Issue if honest work cannot proceed.

Boundary

P0 owns product truth.

P0 does not:
- design tests/evaluators
- choose architecture
- implement product code
- classify DROP / DEFER / RESOLVE NOW
- directly resolve newly discovered human-owned product decisions
- automatically open Wayfinder

When a genuine unresolved product truth should be routed:
→ report Issue in workflow-contracts.md shape
→ outer policy / Decision Management owns routing

Direct founder interaction is still allowed for:
→ phase-level CWO confirmation
→ locating/providing authoritative inputs
→ HUMAN-OWNED RESOLVE NOW decisions routed back by Decision Management

Output

Product Sense changes
+
PhaseResult
v1 regression evidence： Sunrise Café demonstrated no invented booking rules / confirmation / recovery / quality thresholds; barbershop rescheduling demonstrated atomic authority/failure Issues and preserved valid derivations such as a 17:15 latest start. A targeted Gate-2 regression confirmed that absence of a constraint does not establish its opposite.

Regression fixtures

9. P0 Regression Fixtures

v1 不再把預先寫好的 rich Product Sense 當 benchmark；改用薄 Product Idea， 看 skill 是否能自己做 ADMIT / ISSUE / OMIT，而不把 conventional product choices 當成 truth。

Fixture A — Sunrise Café

Build an AI reservation agent for Sunrise Café.

A visitor should be able to use natural-language conversation
to find an available table and make a simulated reservation.

The visitor should not need to understand the café's booking
rules or fill out a traditional reservation form.
Expected pattern例子
ADMITavailable table 必須符合 café booking rules；reservation 是 simulated，不是 real booking。
ISSUEbooking-rule content、simulation / availability-state semantics、reservation authority / confirmation semantics。
OMIT未承諾的 future real booking、tone/persona、任意 latency/turn-count threshold。

Fixture B — One-chair Barbershop Reschedule

Build an AI stand-in for the owner of a one-chair barbershop.

When a customer texts to reschedule, the agent should move the
appointment to a slot that works for both sides.

Scheduling rules: open Tuesday to Saturday, 10:00–18:00;
appointments are 45 minutes; no double-booking.

The owner's calendar is the source of truth for free slots.
Expected pattern例子
Necessary derivation45-minute appointment + closing 18:00 → latest valid start 17:15。
Contradiction test rejects overshootstand-in for owner 不足以推出「per-move owner approval 一定不需要」。
Atomic Issuescustomer confirmation、owner approval、no-workable-slot 等可獨立 routing。
OMIT disciplinetone、latency、buffer、future features 不因可想像就變成 Issue。
為什麼要兩個 fixture： Sunrise Café 測 extremely thin product input；barbershop 測較多 explicit domain rules 與更容易 overshoot 的 authority semantics。 兩個模型在 barbershop fixture 上得到相同 admission pattern，降低「只對單一 prompt 調出來」的風險。

Acceptance

12. v1 Acceptance Criteria

P0 — 已驗證 / freeze

  • ✓ Product Sense normative claims 必須來自 authoritative input 或 necessary implication。
  • ✓ Necessary implication 使用 contradiction test；「沒寫 constraint」不等於可推出其反面。
  • ✓ Unsupported truth 能分成 ISSUE vs OMIT；不把所有 unspecified detail 都變成 Issue。
  • ✓ committed-capability 的 correctness / authority / required-behavior gap 可以形成 Issue。
  • ✓ Issues emitted 時 atomic、independently routable。
  • ✓ 不 invent domain rules、interaction semantics、authority、recovery、quality priority。
  • ✓ Open Questions 不由 P0 自行 DEFER；只有 founder keep-open 或 Decision Management DEFER 才進。
  • ✓ CWO 只描述 outcome，不夾帶 admission/routing procedure。
  • ✓ fresh draft 的 artifact_changes 保持 coarse-grained；Issue ID 不漏進 Product Sense。
  • ✓ 對 Sunrise Café + barbershop fixtures、multiple models，核心 admission behavior 可重現。
Known v1 variance： P0 偶爾可能把 genuine committed-capability gap 清楚留成 unresolved text，但沒有同時 emit Issue。 v1 接受這種 margin-level variance，只要沒有 invent truth、gap 仍可見，而且 downstream phase 在無法誠實前進時會回報 upstream Issue。 不為追求 100% first-pass issue recall 而重新走向 over-Issue。

P1 / cross-phase — 尚待驗證

  • □ P1 使用同一套 PhaseResult / Issue contract。
  • □ P1 不會在 Product Sense ambiguous 時自行新增 product semantics。
  • □ P1 能補抓 P0 遺漏但會阻塞 verification 的 upstream gap。
  • □ uncertainty=false clear defect 可直接 diagnosis / repair。
  • □ uncertainty=true Issue 能正確進 Decision Management。
  • □ DEFER 能保存 future-committed question + concrete revisit trigger。
  • □ Product Sense change 後只更新 affected P1 scope。
  • □ D4 只有 gate passes 時可提出，且一定要 explicit human approval。
  • □ 不需要 phase-local Decision Management，也不需要 separate repair mode。
  • □ 多個完整 integration run 後，若 routing pattern 仍穩定重複，再評估 `/workflow`。

Learning loop

13. 實驗期間要記錄什麼

每次 run 不只記結果，也記 architecture friction：

觀察問題為什麼重要
PhaseResult 哪個欄位常常缺資訊？判斷 contract 是否真的不足。
哪個 Issue 欄位從沒用過？刪掉 speculative schema。
Agent 何時錯把 clear defect 當 uncertainty？改善 Lifecycle vs Decision Management boundary。
Agent 何時偷改 upstream semantics？改善 phase ownership interface。
哪些 routing pattern 重複 3 次以上？候選 orchestrator abstraction。
哪些 step 其實 deterministic？之後可以抽成 script/tool，而不是 skill。
哪些 supporting skill 被反覆使用？確認真正的 reusable skill boundary。

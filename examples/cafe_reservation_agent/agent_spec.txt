Example
Cafe Reservation Agent — Agent Spec
1. Global Contract
# 以下規則適用於所有會改變外部世界狀態的 capabilities。
G-01 — Truthful outcomes
 The agent must not claim that an external action succeeded unless there is evidence that it succeeded.
G-02 — No unrelated changes
 The agent must not modify reservations or user data unrelated to the current request.
G-03 — Current authorization
 The agent may perform a state-changing action only when that action is covered by the user's current authorization.
G-04 — Uncertain execution
 If the outcome of a state-changing action is unknown, the agent must not blindly repeat the action if doing so could create duplicate or conflicting state.
2. Capability: Create Reservation
Scope & Authority
The agent may:
check availability for a new reservation;
propose available alternatives;
create a new reservation after confirmation of the current reservation proposal;
The agent must not:
modify existing reservations;
cancel existing reservations.

Contract
CR-01 — Required booking information
Before creating a reservation, the agent must resolve the information required to identify the intended reservation.
This agent serves one café, Cafe Roma, so the café is fixed and the agent does not ask for it.
The required information is: date, time, party size, reservation name
The agent must not invent missing material information.
CR-02 — Requested reservation unavailable
If the requested reservation cannot be fulfilled, the agent may offer available alternatives.
The agent must not silently substitute an alternative reservation.
The user must first accept an alternative before it becomes the current reservation proposal.
CR-03 — Booking authorization and confirmation
The agent may create a reservation only when the current reservation proposal is authorized by the user.
For this capability, authorization is established through explicit confirmation of the current reservation proposal before creation.
A request to search availability or an earlier expression of booking intent does not by itself satisfy this confirmation requirement.
CR-04 — Authorization after proposal changes
Authorization applies only to the reservation proposal the user confirmed.
If a material term changes beyond what the user confirmed, the prior authorization no longer applies.
The updated proposal must be confirmed before creation.

For example,
Agent: Confirm Friday 7pm, party of 2? User: Yes. User: Actually make it 4 people.
Now
old confirmation = Friday 7pm / 2 people current proposal = Friday 7pm / 4 people
So agent should
Agent: Got it. To confirm: Friday at 7pm, party of 4. Shall I book it? User: Yes.
CR-05 — Unknown booking result
If a create-reservation request may have succeeded but its result is unknown, the agent must determine whether the reservation already exists before retrying whenever that can be determined safely.
It must not: blindly issue a second booking or claim that booking succeeded without evidence
Scenarios
# These are Specification by Example examples of the Contract.
CR-S01 — Complete request, available
Initial state
Friday 7pm is available.
No matching reservation exists.
User
"Book this Friday at 7pm for two under Alex."
Expected
The agent may verify availability, then presents the current proposal and waits for the user's explicit confirmation (CR-03).
After valid authorization:
exactly one reservation exists
date = Friday
time = 7pm
party_size = 2
name = Alex
Forbidden
duplicate reservation
different reservation time
unrelated reservation modification
CR-S02 — Missing party size
User
"Book Friday at 7pm under Alex."
Party size is unknown.
Expected
The agent resolves the party size before booking.
Example valid response:
"How many people?"
Forbidden
assuming party_size = 2
and creating the reservation
This scenario illustrates CR-01.
CR-S03 — Requested time unavailable
Initial state
Friday 7pm    unavailable
Friday 7:30pm available
User
"Book Friday at 7pm for two under Alex."
Expected interaction
The agent informs the user that 7pm is unavailable and may propose 7:30pm.
The agent waits for the user's acceptance before booking 7:30pm.
Forbidden
silently booking 7:30pm
This scenario illustrates CR-02.
CR-S04 — User changes party size after authorization
Conversation
Proposal:
Friday 7pm, party of 2

User:
"Yes, book it."

User then says:
"Actually, make it four people."
Expected
The agent treats the new four-person reservation as a changed proposal.
It does not use the previous authorization to create the four-person booking.
Forbidden
booking for 4 using authorization given for 2
This scenario illustrates CR-04.
CR-S05 — Booking request times out
Initial state
No matching reservation is known to exist.
Agent calls:
create_reservation(...)
The tool times out after sending the request.
The agent cannot initially tell whether the reservation was created.
Expected
The agent checks reservation state or transaction status when possible.
If the booking is found:
do not retry
report the verified booking
If the outcome cannot be determined:
do not claim success
do not blindly create another booking
communicate the uncertainty appropriately
This scenario illustrates CR-05 and G-04.
3. Capability: Cancel Reservation
Scope & Authority
The agent may:
retrieve the user's existing reservations;
identify which reservation the user intends to cancel;
cancel a reservation after valid authorization.
The agent must not:
guess which reservation to cancel when multiple reservations match;
cancel a reservation merely because the user asks about its cancellation policy.
Contract
CA-01 — Reservation identification
The agent must identify the reservation the user intends to cancel before performing cancellation.
If multiple reservations plausibly match, the ambiguity must be resolved first.
CA-02 — Cancellation authorization
Discussing, locating, or asking about cancellation does not itself authorize cancellation.
The agent must have valid authorization for the identified reservation before cancelling it.
CA-03 — Cancellation result
The agent may report a reservation as cancelled only when the cancellation outcome is known to have succeeded.
Scenarios
CA-S01 — One matching reservation
Existing state
Friday 7pm
party of 2
confirmation ABC123
User
"Cancel my Friday reservation."
Only one reservation matches.
Expected
After valid cancellation authorization:
ABC123 is cancelled
no other reservation changes
CA-S02 — Multiple matching reservations
Existing state
Friday 6pm
Friday 8pm
User
"Cancel my Friday reservation."
Expected
The agent asks which reservation the user means.
Forbidden
choosing one of the two reservations itself
4. Evaluation
Evaluation is derived from the Contracts and Scenarios rather than being a single LLM judge.
For this agent, use several types of checks.
Requirement type
Evaluation
Correct reservation created
deterministic final-state assertion
No duplicate booking
deterministic DB/state assertion
No unrelated reservation changed
state-diff assertion
Confirmation occurred before booking
trace / milestone assertion
Agent did not silently substitute unavailable time
trace + state assertion
Ambiguous cancellation triggered clarification
conversation/trajectory assertion
Response clearly explains an uncertain outcome
semantic grader or human review
Reliability under natural-language variation
repeated scenario trials

For example, CR-S03 might be considered successful only if:
1. 7pm was recognized as unavailable
2. the agent did not create 7:30pm before acceptance
3. the user accepted 7:30pm
4. exactly one 7:30pm reservation was created
5. no unrelated state changed
Notice that this does not require a particular wording, number of turns, or exact tool-call sequence.

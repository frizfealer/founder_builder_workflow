verify-artifact, visualized

A shared checker that every phase skill runs on its own output before the owner is asked to confirm it. This page walks through why it is shaped the way it is, then follows one finding from start to finish.

1. One mechanism here, one standard per artifact elsewhere

The skill splits the work in two. verify-artifact owns how verification runs. Each producing skill (for example product-definition, which writes product-sense.md) owns what failure looks like for its own artifact.

Lives in skills/verify-artifact/Lives beside each producing skill's SKILL.md
This procedure: stages 1 to 5, the four cross-artifact rules, resolution rulesVERIFY.md: the standard. Names the sources, the check IDs, their severity, the finder families, the Nit cap
scripts/verify_lib.py: quote lookup, section parsing, open-marker counting, write-scope diff, the failure Reportscripts/verify_mechanical.py: that artifact's D-checks (headings, IDs, markers). Imports verify_lib
scripts/verify_generic.py: three CLI modes every artifact needs (findings, status, write-scope)fixtures/planted/: known-good copies with one planted defect each, for smoke testing the standard
assets/verification-report.template.md

D-checks are the mechanical checks a VERIFY.md lists, numbered D-1, D-2, and so on. Nothing in verify-artifact knows about Product Sense, Agent Spec, or any other kind. The skill refuses to run without a VERIFY.md, and it never adds a check that is not in VERIFY.md or in the four shared rules.

2. The author's model can't be trusted to judge its own gap-filling

Concrete case: the Product Idea says guests can book a table. The drafting agent writes "a reservation is held for 15 minutes." That number sounds reasonable, so a reviewer built on the same model, asked "does this look right?", will likely nod. Nobody stated it.

The general rule follows. The main failure these checks target is filling gaps with plausible defaults, and the reviewing model shares that habit with the author. So the skill's design goal is a feedback signal the author can loop on (produce, verify, fix, re-verify) whose source is, as far as possible, not the same model's judgment.

Three design choices follow from that goal

1. Mechanical checks run first and gate everything else.

2. Finders are narrow and adversarial. They fill a table that asks "where is the span?", not "does this look right?"

3. The author has no way to close a finding by saying it is fine.

Every later section is one of these three choices worked out in detail.

3. Five stages, with two ways back to the author

Read the diagram left to right on the top row, then right to left on the bottom row. Border color tells you who produces the signal at that stage.

The two dashed lines are the point of the skill. The author keeps looping until the cheap exact signal is clean, then until no Important is open. Owner confirmation comes after, and this skill does not perform it.

4. A missing input must fail loudly, because silence reads as a pass

If the gaps finder never sees the recorded commitments, it cannot tell which capabilities are committed, so it cannot flag a committed capability whose gap was left unmarked (PS-5 for product-sense.md). It returns nothing, and the loop reads nothing as "pass." So every input below is required. If one is missing, the report says inputs: incomplete and the run cannot claim a pass.

InputWhat breaks without it
The artifact (path)Nothing to verify
Its VERIFY.mdNo standard; the skill never verifies without one
Authoritative sources named in VERIFY.md (Product Idea, product-sense.md, agent_spec.md, example-map.md, …)Traceability cannot be checked
Confirmed phase objective and recorded commitmentsCannot judge whether a gap should be left open or simply omitted
--prior version, on a scoped updateWrite scope cannot be checked
Declared changed scope, on a scoped updateSame

5. Four rules apply to every artifact on top of its own VERIFY.md

Two terms first. An open truth is a fact the sources do not settle. An open marker is the sentence the artifact writes where that fact's value would go, such as "The hold window is unresolved and deliberately not stated." Each VERIFY.md defines its markers. An OMIT statement is the sentence for a fact the sources do not settle and no commitment needs, such as "No hold window is established by the authoritative inputs." It is complete as written: it is not an open marker, and nobody answers it.

RulePasses whenIf violated
1. TraceabilityEvery statement points at a source: a rule ID, a quoted span from an authoritative input, or a fact in an upstream artifact. VERIFY.md defines "statement" and "source" for its kindImportant
2. Write scopeOnly declared files and sections changed. On a scoped update, only the declared scope differs from --priorImportant
3. Gaps stay openWhere sources are silent, the artifact uses an open marker or an OMIT statement instead of decidingAuthored decision with no source: Important. If a commitment needs the value, the fix replaces it with an open marker, and the verifier writes the open-truth line. If no commitment needs it, the fix replaces it with the OMIT statement VERIFY.md defines, and nothing is reported.
Problem in the source itself (contradiction, ambiguity): Pre-existing, reported to the upstream owner
4. Done-when needs evidenceAny "tests pass" or "validated" claim comes with the output that shows itImportant

6. Each stage spends model effort only where scripts can't decide

Stage 1: mechanical checks gate everything

script

Three scripts run in this order:

  1. The script on the mechanical: line of the artifact's VERIFY.md, by convention <producing skill>/scripts/verify_mechanical.py. It runs that kind's D-checks: structure, IDs, citation quotes found verbatim.
  2. verify_generic.py status. The header Status: Draft — N open must equal the number of open markers, as the artifact's VERIFY.md defines them. Status: Confirmed requires zero.
  3. verify_generic.py write-scope, only on a scoped update. Any section outside the declared scope that differs from --prior fails.

Every failure is an Important with exact locations, written to the report before any model runs. The author fixes and re-runs Stage 1 until it is clean. Stage 2 does not start on a failing Stage 1.

Example of the status check. Both sentences below are open markers in product-sense.md's VERIFY.md (D-2):

# product-sense.md, top of file
Status: Draft — 1 open

# elsewhere in the artifact: two open markers
The hold window is unresolved and deliberately not stated.
Cancellation fees are unresolved and deliberately not stated.

# output
ST     product-sense.md                         Status says 1 open, artifact has 2 open marker(s)
status: 1 failure(s)

Stage 2: finders fill tables, they don't review

model, fresh context, one per family, in parallel

VERIFY.md groups its checks into families. For product-sense.md they are Traceability, Gaps & open truths, and Boundary & scope. Each finder sees only the artifact, the sources, the inputs, and its own family's checks. It does not see the producing conversation, the other families, or the other finders.

The traceability finder's whole job is this table. Every none row becomes a candidate finding.

statementsource quotenone
Guests can book a table through the chat assistant."guests book a table by chatting with the assistant" (product-idea.md)
A reservation is held for 15 minutes past the booking time.none

Rows are illustrative, for a made-up restaurant booking product.

Other families get the same treatment. SKILL.md's example is an authority finder that lists every action the artifact grants, each with its span or none. In product-sense.md's VERIFY.md that check (PS-11, silent authority) sits inside the Traceability family instead of its own.

A finder that returns prose instead of its table is re-run. If a second model family is available (the codex-rescue route is the existing example), the traceability and gaps families run on it. Same-model finders are acceptable for structural families.

Stage 3: the verifier drops anything without quoted evidence

mixed, fresh context, one verifier

The verifier receives the artifact, the sources, and the merged candidate list. Each candidate passes three gates in order, and failing any gate drops it with a logged reason.

GateQuestionWho decidesCode in verify_generic.py findings
(a)Does the quoted artifact text exist verbatim?scriptFa
(b)Does the quoted source text exist verbatim? If the finder claimed none, does that hold after searching the sources?script for existence. model only for none claims the script couldn't disproveFb
(c)Does the quoted evidence actually support the stated failure?modelnone

"Verbatim" is lenient about whitespace and curly versus straight quotes (verify_lib.normalize), and strict about everything else. After the gates, duplicates across finders are merged. Then the Nit cap from VERIFY.md is applied once to the merged list, not per finder, keeping the Nits with the strongest evidence. For product-sense.md the cap is 5.

Stage 4: one report file, written beside the artifact

output

The verifier writes verification-report.md from the template, and writes nothing else. Severity is whatever VERIFY.md assigns the check. A verified problem that no check lists defaults to Nit.

Pre-existing findings and rule-3 gaps fixed with an open marker go into the Open truths for the owner block, one line each, in this shape:

- <unresolved truth> · evidence: "<span>" (<location>) · decides: <founder | spec owner | …>

The producing skill then repeats those lines in its reply and makes sure each one has an open marker in the artifact.

7. Only Importants block; Pre-existing problems belong to someone else

SeverityComes fromBlocks confirmation?Who acts
ImportantAny Stage 1 failure, any check VERIFY.md marks Important, any violation of the four rulesYes, while openProducing skill must fix, refute, or get owner resolution
NitChecks VERIFY.md marks Nit, plus verified problems no check lists. Capped after mergeNo; may stay openProducing skill, optionally
Pre-existingA real problem in an upstream source: two sources contradict, or one is ambiguousNot counted against this artifactThe upstream owner, via an open-truth line

Wording problems are a Nit at most, and only if VERIFY.md lists them. This is not a style reviewer.

8. An Important closes in exactly three ways, and none of them is the author's say-so

OutcomeWhat has to happenConfirmed by
FixedThe artifact changedThe next verification run no longer reproduces the finding
RefutedThe producing skill supplies a verbatim source span the finder missed, at a stated locationscript confirms the span exists, then the verifier confirms it supports the statement
Owner-resolvedThe accountable human owner closes it with a reasonRecorded in the report with the owner's name. Not available to the producing agent
What is ruled out

"Resolved: this is standard practice" is not an outcome. A finding the author disagrees with and cannot refute with a span stays open, and open Importants block confirmation.

Verification is closed when no Important is open. That closes gate 1 of the two gates in the next section.

9. An artifact stays a draft until two gates close, in order

GateCloses whenWho closes it
1. Verification closedThis skill ran against the producing skill's VERIFY.md, inputs were complete, and no Important is openThis skill. Its run ends here
2. Owner confirmationThe accountable human owner confirms the artifact after seeing the closed verification report, and only when the artifact has zero open markersThe owner, outside this skill

Gate 2 needs every open truth settled first. Concrete case: product-sense.md still says "The hold window is unresolved and deliberately not stated," so the founder cannot confirm it yet. The founder settles it in one of three ways the producing skill defines: answer it, defer it, or drop it.

  1. The founder answers: "Hold the table 10 minutes, then release it."
  2. The answer is appended verbatim and dated to the ## Clarifications section of product-idea.md. That section is an authoritative source.
  3. /product-definition reruns the affected section. The open marker becomes "A table is held for 10 minutes past the booking time," and the header count drops by one.
  4. Verification reruns on that scope, and the new statement traces to the founder's dated line.
  5. At zero open markers, the producing skill sets Status: Confirmed. verify_generic.py status rejects Confirmed while any marker remains.

Until both gates close, the artifact is a draft. Downstream phases may read it to prepare, but any truth they take from it is unconfirmed. A scoped update reopens both gates, for the changed scope only.

10. One finding, end to end

Illustrative walkthrough. The product and the sentences are made up. The check IDs, scripts, and rules are the real ones from skills/product-definition/VERIFY.md and this skill.

Setup: product-idea.md says guests book a table by chatting with the assistant, and says nothing about how long a table is held. Booking is a committed capability, and it cannot be stated correctly without the hold window, so this gap must stay open rather than be omitted. The drafted product-sense.md contains "A reservation is held for 15 minutes past the booking time."

  1. Stage 1 passes. All eight headings are present and in order (D-1). No TBD or TODO (D-2). The header says Draft — 2 open and there are two open markers (D-3). The scripts cannot see a guessed number, so this stage has nothing to say about it.
  2. Stage 2 flags it. The traceability finder writes the statement with none in the source column and labels it PS-4, guessed value. Separately, it also claims none for "Guests can book a table through the chat assistant." That second claim is wrong.
  3. Stage 3 keeps one, drops one. For the 15-minute candidate: (a) the script finds the artifact quote verbatim; (b) the source is a none claim, so the model searches product-idea.md and finds no hold window; (c) the evidence fits PS-4. It becomes V-01, Important. The booking candidate is dropped at (b): none claim disproved, span found in product-idea.md.
  4. Stage 4 reports it. V-01 — PS-4: guessed value, with source: none — searched product-idea.md. Because this is an authored decision with no source (rule 3) and booking needs the value, the verifier also writes an open-truth line: How long a reservation is held past booking time · evidence: none in product-idea.md · decides: founder.
  5. Stage 5 refuses a shortcut. The author replies "15 minutes is the industry norm." That is not a span, so V-01 stays open and blocks confirmation.
  6. The author fixes it. The sentence becomes "The hold window is unresolved and deliberately not stated." The header must now read Draft — 3 open. If the author forgets to update it, Stage 1's status check fails on the next run. That is the loop catching the fix's own side effect.
  7. Re-verification closes it. The next run no longer reproduces V-01, so it is marked fixed. With no Important open, verification is closed (gate 1). The artifact still has three open markers, so the founder settles each one, as section 9 shows, before confirming (gate 2).

11. Check yourself

Answer each question before opening it.

Stage 1 reports only a status-header mismatch. Do the finders run while the author fixes it?

No. Stage 2 does not start on a failing Stage 1. Model effort is spent only on artifacts that already have the right shape.

Why is the traceability finder told to fill a table instead of reviewing the artifact?

The failure it hunts, filling gaps with plausible defaults, is a habit the finder's model shares with the author. Asked "does this look right?", it under-reports. Asked "where is the span?", a missing span is visible as an empty cell.

The Product Idea says cancellations are free in one place and charged in another, and the artifact picked "free." Is that an Important against the artifact?

The contradiction itself is Pre-existing: a problem in the source, reported as an open truth for the upstream owner and not counted against this artifact. For product-sense.md this is PS-PRE-1 or PS-PRE-2. The author should not have resolved it either way.

A finder reports 4 Nits and another reports 4 Nits. The Nit cap is 5. How many Nits reach the report?

At most 5. The cap applies once, after merging and verifying across all finders, keeping the Nits with the strongest evidence. It is not 5 per finder.

The finders never received the recorded commitments, and they found nothing. Can the report say verification passed?

No. The run is inputs: incomplete, and an incomplete run cannot report a pass.

Verification is closed, but the artifact still has two open markers. Can the owner confirm it?

No. Gate 2 requires zero open markers. The owner first answers, defers, or drops each open truth. An answer goes into the sources, the producing skill reruns, and verification reruns on that scope. verify_generic.py status rejects Status: Confirmed while any marker remains.

12. Reference

Script commands

Exit codes for both scripts: 0 pass, 1 failures, 2 usage error.

uv run python skills/verify-artifact/scripts/verify_generic.py findings --findings candidates.yaml --artifact product-sense.md --sources product-idea.md
uv run python skills/verify-artifact/scripts/verify_generic.py status --artifact product-sense.md
uv run python skills/verify-artifact/scripts/verify_generic.py write-scope --artifact product-sense.md --prior old/product-sense.md --scope "Product Scope"

The findings file is YAML: a list, or {findings: [...]}. Each item has id, artifact (quote), and source (quote, none, or text starting "no source found"). Failure codes: Fa artifact quote, Fb source quote, ST status header, WS write scope.

Smoke test after editing a VERIFY.md

fixtures/planted/ holds two or three known-good artifacts with one defect planted per copy, each named for the check it should trigger, for example PS-1-over-admission.md. After editing a VERIFY.md or this skill, run verification on each fixture once and confirm the named check fires. It answers one question: does the signal still detect what it was built for. It is run by hand and is not an eval program.

What this skill is not

  • Not a runtime judge. It checks artifacts at authoring time. Judging agent responses at runtime belongs to the evaluation implementation.
  • Not a style reviewer. Wording is a Nit at most, and only if VERIFY.md lists it.
  • Not an escalation path. It reports open truths. Whether to answer, defer, or drop them is the owner's call.
  • No voting. Mandatory quoted evidence plus scripted quote-existence controls false positives. A second verifier is added only if the owner-overturn rate in reports calls for it.

Notes on the source

One small inconsistency turned up while building this page. It is reported here rather than smoothed over.

  • Stage 1 says to run verify_generic.py status and write-scope after the skill-owned script. The product-definition script already runs both (as D-3 and D-W), so those checks run twice and report under two codes. The generic status run also counts verify_lib.OPEN_MARKERS_DEFAULT unless --markers is passed. That list has two markers D-3 does not count (Status: rough and | assumed |), so the two runs can disagree.

# Eval harness for the new agent-spec format: plan

Written 2026-11-14 against `DECISIONS.md` at commit `688e9e7`. Nothing else was changed. Terms used below. A **trial** is one run of the skill on frozen inputs. A **kind** is a family of
trials that are graded against each other. A metric is **gated** when one bad trial fails the
change, and **reported** when it is only shown. A **judge** is a fresh LLM subagent that rules where
no program can. The **policy model** is a small program that states the policy as states and steps;
the **checker** walks every state it can reach and tests every rule there. A **break** is a rule
that fails in some reachable state; its **shortest path** is the fewest steps that reach it.

## 1. What a new-format spec consists of

No template for the new format exists yet. Every file layout below is an **assumption** this plan
pins so the harness can be built first; the format switch adopts it or changes it with the harness.

| File | Holds | Program-readable? |
|---|---|---|
| `index.md` | One page linking the three owner pages. | Yes: links resolve. |
| `claims.md` | One table row per claim about an outside system or the business. Columns (assumed): id, claim, kind (system / policy / limit / money / missing), source (owner's words / proposed, accepted / spec only / nobody), packet citation, rules that depend on it, and two guard columns: "what ends it" for a limit set to none, "if it differs from what the customer confirmed" for a money value passed on from a tool. One row per outside system names its owner and its docs. | Yes: table parse; quotes checked against the packet. The truth of a claim is not. |
| `rules.md` | The rules in the owner's words, each with an id and the claims rows and decision it rests on, then the decision log. | Ids and citations, yes. Whether a rule says what the owner said, no. |
| `model.py` | The policy model. **Assumption:** standard-library Python with the interface of the 2026-11-14 prototype (state, steps for agent, customer and outside systems, a rules list with step and end checks), plus one deliberately broken rule for the self-test. | Yes: it runs. |
| `policy.md` + `chart.mmd` | Generated by the checker: the chart, then each break as its shortest path in plain steps. | Yes: arrow count, and each break listed matches the checker's output. |
| `scenarios.md` | Derived scenarios. Each is either a model path (cites the path) or a conversational case the model cannot express (marked so). Each cites a rule. Pinned per spec version. | Yes: structure, citations, and replay on the model. |
| `interview-log.json` | Every question asked, its recommended answer, and the reply. A trial output, not a spec file. | Yes. |

The prototype shows the model and checker are feasible on this product: 8,772 states, 5 breaks
with shortest paths, a passing self-test, and 25 of 31 scenario rows mapping to exactly one path
(`statechart-test/report.md`).

## 2. The fixture

The fixture is what every trial starts from, frozen: `product-idea.md`, the recorded owner answers
in `review-packet.md` ("Interview, verbatim" and "Tool confirmation turn"), and one new file,
`owner-brief.md`, holding the facts the guard's first question asks for (which systems the agent
calls, who owns each, where their docs are). The packet does not record those facts.

The current `build` kind replays the recorded questions verbatim, so it cannot test the guard. The
new kind, `build2`, replaces replay with an **owner stand-in**: a subagent that sees only the
fixture files and answers each question the skill asks. If the packet or the brief answers it, the
stand-in gives that answer verbatim. Otherwise it accepts the skill's recommended answer, and the
question is logged as a stand-in default. It never invents a fact.

This tests the guard's visible effects: every question carries a recommendation, the first question
reaches the systems rows, every limit set to none gets an end, and every money value passed on gets
a mismatch rule. It does not test whether the guard's questions are the right ones for a real
owner, because a stand-in cannot be surprised. That needs a person.

A second fixture, `seeded/`, is a hand-made new-format version of `round0-agent-spec.md` that keeps
round0's known defects. It tests the grading scripts only; no skill trial runs on it.

## 3. Metrics

Baseline "build2" means the worst value over three build2 trials of the switched skill (step 8).
Every gated metric not marked absolute is also held to that worst value plus the 10 % tolerance.

| Metric | Counts | Out of | How | Gate | Baseline |
|---|---|---|---|---|---|
| integrity | failures of the skill's own scripts; checker ends at 0 errors; no message to the user | - | code | gated, pass | absolute |
| lint_errors | lint errors in the final spec (missing claims fields, scenario with no rule, duplicate ids, broken links) | - | code | gated, = 0 | absolute |
| checker_selftest | the frozen checker runs the trial's model, and its broken rule yields a break | - | code | gated, pass | absolute |
| unlisted_breaks | breaks the frozen checker finds that `policy.md` does not list | breaks found | code | gated, = 0 | absolute |
| listed_breaks | breaks on the policy page, each an owner decision | - | code | reported | build2 |
| one_path_share | model-path scenarios that replay to exactly one path | model-path scenarios | code | gated, higher | build2 (prototype on round0: 25 / 31 = 0.81, for reference) |
| quote_valid | claims rows sourced "owner's words" whose quote is in the packet verbatim | such rows | code | gated, = 1.0 | absolute |
| unsourced_claims | claims rows sourced "nobody" or "spec only" | - | code | reported | build2 |
| answer_reach | recorded answer units cited by a rule or claims row | 23 units (my count: round 1 four, round 2 eight, round 3 four, summary three, tool turn four; frozen as a list in step 6) | code | gated, higher | build2 |
| guard_recommend | questions with a recommended answer | questions asked | code | gated, = 1.0 | absolute |
| guard_none_limits | limit rows set to none with "what ends it" filled | such rows | code | gated, = 1.0 | absolute |
| guard_money | money rows with the mismatch column filled | such rows | code | gated, = 1.0 | absolute |
| guard_systems | each system named by a tool has a row with owner and docs | systems | code | gated, = 1.0 | absolute |
| key_recall | draft-key defects (section 4) that the final spec avoids or puts to the owner as a decision | 9 | judge | gated, higher | build2 |
| unsupported_statements | product facts in rules or scenarios with no claims row and no support in the inputs | - | judge | reported | build2 |
| owner_lines | non-blank lines of `index.md`, `claims.md`, `rules.md`, `policy.md` | - | code | gated, lower | build2 |
| chart_arrows | arrows in `chart.mmd` | - | code | reported | DECISIONS asks for about 20; prototype had 28 |
| stand_in_defaults | questions answered by accepting the recommendation | questions asked | code | reported | build2 |
| wall_clock_s, tokens_total_k, cost_usd, effort | as today | - | code | wall clock gated, rest reported | build2 |

Two judges remain, because whether a defect is still present and whether a fact is supported are
readings, not counts. The key_recall judge is checked once against the owner's 20 rulings in
`calibration/2026-11-11/answers.md`: it rules each of the 20 findings Real, Not real or Style only
on the same spec excerpt the owner saw, and passes at 18 of 20 or better (the 90 % bar in
skill-iterate's calibration reference). This checks its judgment of a defect, not the new question
"is it still present", which the rulings cannot test. unsupported_statements is reported, not gated:
it was 0 in all three build baselines and was never calibrated, so it carries no signal yet.

Grading scripts are frozen copies inside `eval/agent-spec/new-format/grader/`, not the skill's own
lint and checker. If the harness used the skill's scripts, a skill change would change the
measurement in the same iteration, which skill-iterate rule 5 forbids.

## 4. The answer key

The 50 clusters of `key-proposal.md`, sorted. Its header says 9 key-item, 27 round0 and 14 fix
clusters, but its tables list 8, 29 and 13; the total of 50 matches.

| Group | Count | Clusters |
|---|---|---|
| Still a defect in the new format | 9 | M1, M3, P7, P10, P21, P25, P26, F2, F8 |
| Becomes a program check | 13 | M2, M7, M8, M10, M11, P1, P2, P6, P11, P12, P18, P29, F5 |
| Moves to agent eval | 27 | M9, P3, P4, P5, P8, P9, P13, P14, P15, P16, P17, P19, P20, P22, P23, P24, P27, P28, F1, F3, F6, F7, F9, F10, F11, F12, F13 |
| No longer exists | 1 | F4 |

How they were sorted. A defect stays when a rule or claim could still be wrong in the new files and
no program can see it, mostly a rule that departs from the owner's answer. It becomes a program check
when the checker or scenario replay would report it: two rules disagreeing in a reachable state, a
scenario that maps to no path or to several, a step no scenario takes, or an answer no rule cites. It
moves to agent eval when it is about rubric wording, trial mechanics or what the simulated user
knows, all of which DECISIONS gives to agent eval. F4 is gone because scenarios are regenerated from
the model, so a scenario cannot lag behind a changed rule.

The draft key, the first group:

- **M1.** After the second cancel goes unanswered, the agent hands off without the re-read the owner asked for (round 3 Q4).
- **M3.** The failed-refund message says "the refund has not been issued" where the owner said "not confirmed yet" (round 3 Q3).
- **P7.** Nothing says what happens when the customer names a second order; no input sets the one-order limit.
- **P10.** One unanswered lookup is treated as final though lookups may be retried without limit; nothing says what ends the retries.
- **P21.** After a timed-out first refund call, the failed or unavailable branches skip the re-read the owner required.
- **P25.** No claim says how the order system reads an order number typed in another case ("hg-10530").
- **P26.** A "yes" and a withdrawal in the same message are covered by no rule.
- **F2.** Whether an unanswered cancel can take effect after a lookup showed the order open; no input settles it.
- **F8.** The ban on promising when money arrives is narrowed to dates and time spans, against "promises nothing about when".

Two program-check items, P11 and P18, need a model that tracks proposal terms; the prototype merged
them into one value. If the seeded model cannot express them, they are recorded as not checkable.

## 6. Build order

Costs use `grading.json` model_rates (opus blended $7.84 per million tokens) and the build
baselines (build-base-1..3: $9.24 to $9.57 and 2,103 to 2,354 s per trial). Judge costs are not
recorded anywhere in the repo, so judge estimates assume 100k to 200k tokens per call, unverified.

1. **Pin the format.** `new-format/FORMAT.md`: section 1's files, columns and model interface.
   Done when lint (step 3) accepts the seeded fixture's clean copy. No trials, $0.
2. **Seeded fixture.** Write `seeded/` from `round0-agent-spec.md` and `review-packet.md` in the
   pinned format, carrying the 13 program-check defects. The prototypes are reference only. Done
   when every file of section 1 exists and a list maps each defect to its line. No trials.
3. **Frozen lint.** `grader/lint.py` with tests. Done when the clean copy gives 0 errors and the
   seeded copy reports P12 as a rule with no source and P29 as an uncited answer. No trials, $0.
4. **Frozen checker and replay.** `grader/check.py`. Done when, on `seeded/`, it reports breaks or
   path results for each program-check defect it can express, passes the self-test, and gives 0
   breaks on a fixed copy. No trials, $0.
5. **grade.py.** Add section 3's code metrics to `grade.py` and to the grading-schema list in one
   commit, and draft `grading-new.json` with the `build2` kind. Done when `grade.py` prints a table
   for a hand-written `trial.json` on `seeded/`. No trials, $0.
6. **Answer units and key judge.** Freeze the 23 answer units and the 9-item key; write the
   key_recall judge task; run it on the 20 calibration items. Done at 18 of 20 agreement. 20 judge
   calls, about $16 to $31 (20 x 100k to 200k tokens x $7.84 per million).
7. **Stand-in and run prompt.** `owner-brief.md`, the stand-in brief, `PROMPT-build2.md`. Done when
   one trial of the current skill, run with the stand-in, gives the recorded answer verbatim to every
   recorded question. 1 trial, about $9.40 and 37 minutes (build-base mean).
8. **After the format switch: baseline.** Three build2 trials of the switched skill, graded. Done
   when the table has no pending value. 3 trials, about $28 plus about $5 to $10 of judges.

Total before the switch: 1 trial and 20 judge calls, about $25 to $40.

## 7. Decisions for the owner

1. **Owner brief.** I draft `owner-brief.md` from the product idea and the packet: three systems
   (the order system, which also issues refunds; the payment provider behind it; the staff task
   queue), all owned by Harbor Goods, no docs. You confirm or correct it. If you veto, the guard's
   first question is not tested.
2. **Stand-in accepts the recommendation where the record is silent.** Those answers become fixture
   truth for build2 and are counted in stand_in_defaults. If you veto, a trial stops at the first
   unrecorded question, and the harness tests no part of the guard.
3. **The 9-item draft key** (section 4) becomes the build2 key. If you veto, key_recall is reported,
   not gated, until you rule on the items.
4. **Three calibration rulings are read by their reason, not their label.** F2 is labelled "Not
   Real" but says it should be Important, so Real. F7 and F12 are labelled "Real" but the reason says
   Style only, so Style only. If you veto, the three leave the set and the judge passes at 16 of 17.
5. **Retire the old kinds and close the queued experiments** (section 5). If you veto, the named
   experiments stay queued, though none can run on the new-format skill.

## Decided here, with reasons

- Grading scripts are frozen copies, not the skill's (rule 5: measurement and skill change apart).
- unsupported_statements is reported, not gated: 0 in all build baselines, never calibrated.
- owner_lines is gated against growth only, so a change cannot pass by making the owner read more.
- chart_arrows is reported: "about 20" in DECISIONS is a target, not a threshold.
- One new kind only. A verify-only kind would need a new-format round0, which does not exist.

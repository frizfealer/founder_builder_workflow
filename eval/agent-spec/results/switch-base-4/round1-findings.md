F1 | Gap | Important | rules.md R-13, D-13; claims.md C-46, C-22, C-35; rules.md "What the agent does" row "a read got no answer"
Quote: "When a read gets no answer, the agent sends it again; the owner set no limit on reads. Only a read that fails with an error counts as a failed read."
Evidence: Q10 put this exact path to the owner: the order list call gets no answer again and again, "the agent never answers the customer. What ends it?" The owner's reply only repeated "Reads may be retried on timeout without limit; only commit calls are bounded." The spec admits the loop has no end. C-46's "what ends it" column says "nothing the owner set: the agent reads again until the read answers or fails with an error (open question)". But rules.md R-13 and D-13 state it as a settled decision and do not mark it as open. The only end the spec offers is "fails with an error", and that is an outcome the owner never confirmed. In Q6 the list call answers with the orders "or gets no answer", and C-35, which adds "fails with an error", is labelled "spec only". The same unbounded loop sits under every re-read: the read after a cancel call with no answer (R-11), and the read after the second refund call (R-08; C-22's "then the re-read" is the end it names). So after a cancel or refund that may have gone through, the agent can sit silent forever.
Pattern: A repeated call whose only stopping condition is an outcome nobody confirmed, while the owner's question about what ends it is left open and the rules page presents it as decided.

Verifier: F1 | Real | Important | I could not refute this one. The finding fits the Gap example "a repeated thing with no end". Q10 asked the owner "What ends it?" and the reply only repeated "Reads may be retried on timeout without limit". The spec contradicts itself: C-46's "what ends it" column says "(open question)", but R-13 and D-13 state the answer as settled. The only end it names, "fails with an error", comes from C-35, which is marked "spec only". The severity could be argued down to Nit, because unlimited reads is what the owner literally said. I left it Important because the owner never answered what ends the loop, and an agent built from this spec can stay silent with the customer indefinitely.
Decision: kept, Important. Status: fixed. R-13 now says what ends a read that never answers is an open question, and carries the message for a first read that fails (owner accepted, Q14); D-13 says the end is left open. The question itself is open in the report.

F8 | Unclear | Nit | claims.md C-18, C-19, C-20; rules.md R-08, D-03
Quote: C-18: "A refund call that ends in a lasting error returns a refund with status failed." R-08: "After a refund call that answers with an error or gets no answer, the agent sends the refund call once more ... After a failed refund, or an answer that the order is not cancelled, it sends none."
Evidence: "lasting error" and "passing error" are terms the spec coined for the owner's "terminal" and "transient". They are first used in C-18 and C-19 but defined only at C-48. In rules.md, R-08 uses "an error" to mean only the passing error, while a lasting error appears as "a failed refund". Nothing on the rules page ties the two together. D-03 then switches back to "passing refund error" and "lasting error". An owner reading R-08 could take "an error" to include a declined card and expect a retry, which the owner said must not happen ("none on a terminal one", Q5 case 2).
Pattern: A coined term used before its definition, and used under different names on different pages.

Verifier: F8 | Real | Nit | I could not refute the coined-term part. "lasting error" first appears in C-18 (claims.md, the first page in the reading order) with no definition. It is defined only at C-48, and on the rules page only in D-03's reason column. The R-08 half is weaker. C-31 and the Q6 tool set treat "answers with a failed refund" and "answers with an error and creates none" as separate outcomes, and R-08 sends no retry after "a failed refund". So a declined card (a refund with status failed, C-18) does not fall under R-08's "an error". The placement defect stands either way.
Decision: kept, Nit. Status: open. "Passing error" and "lasting error" are now defined at the top of claims.md and rules.md, and the rows and model labels use them. The change to R-08's text went to the owner (Q16); the reply quoted the record without accepting, so it stays a proposal in the report.

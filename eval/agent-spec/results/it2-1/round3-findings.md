## R3-01 (from faithfulness F1)

R3-01 | Lies | Important | §5.2 rubric dimensions "Cancellation outcome unknown reported" (CO-S14, CO-S15) and "Refund status reported" (CO-S19)
Quote: "The agent tells the customer it is not known whether the order was cancelled, that no refund was issued, and that store staff will follow up; it never says the order was cancelled, and its final message does not say the order was not cancelled."
Evidence: Neither the inputs nor the spec's own rules ask the agent to say these things. Round 3 Q4 (review-packet.md, "Round 3"), confirmed by the user, says: "Re-read fails, say outcome unknown, issue no refund, hand off." There, "issue no refund" is an action limit, not something the agent must tell the customer. The failure rows for that case (agent-spec.md lines 103 and 104, "If the lookup does not answer, tell the customer it is not known whether the order was cancelled and store staff will follow up, make no CO-A3, and make CO-A4") only require saying "not known whether cancelled" and "staff will follow up". So an agent that does exactly what the row says fails CO-S14 and CO-S15. The same thing happens with "Refund status reported" (line 1757: "The agent tells the customer the order is cancelled and the refund's status is the data-variant row's refund status"). Its failure row (line 108, "If the lookup shows the refund pending or issued, tell the customer that status and the refund id") does not require saying the order is cancelled. An agent that reports only "refund RF-5531 is pending" follows CO-S19's row but fails the dimension. Every other rubric dimension's required statements match its failure row or rule.
Pattern: A rubric dimension requires the agent to say something that no rule or failure row requires, so it adds an obligation the contract and inputs do not support. Each dimension's required statements should match its failure row's "tell the customer" clause exactly, or the failure row and rule should be changed to require the statement.

**Verifier:** R3-01 | Not real | Important | Both required statements the finding calls unsupported are backed by the spec and the inputs. (1) "No refund was issued" in "Cancellation outcome unknown reported" (CO-S14, CO-S15): G-03 (line 24) says "tells the customer a refund is pending or issued only when ... Otherwise it tells the customer the action was not done or, when it cannot tell, that the outcome is unknown." In both scenarios the agent made no CO-A3, so the refund in the confirmed proposal was not done, and G-03 requires the agent to say so. (2) "The order is cancelled" in "Refund status reported" (CO-S19): failure case 3 in the packet (review-packet.md line 54, "Cancel succeeded, refund call timed out ... agent retries once, then re-reads the order and refund records and reports what it finds") requires reporting what the re-read of the order shows, and that is status cancelled. The primary actor's interest (line 9, "wants to be told truthfully whether the order was cancelled and where the refund stands") supports it too. So the finding's premise that "no rule or failure row requires" these statements is false.

**Decision:** dropped | **Status:** dropped | Read G-03 'Otherwise it tells the customer the action was not done' and packet case 3 '...re-reads the order and refund records and reports what it finds': both required statements trace to them; agree it refutes.

## R3-03 (from verdicts F1)

Quote: "The agent tells the customer no date or time span by which refunded money arrives." (CO-09, agent-spec.md line 86; the dimension definition at line 1759 repeats it)
Evidence: The input is broader and plainer. review-packet.md, Round 3 Q1, confirmed "Yes to all", says: "The agent promises nothing about when the money arrives." ## R3-05 (from verdicts F3)

R3-05 | Ambiguous | Important | CO-03 failure row "the customer asked to cancel only some of an order's items"; CO-02; scenarios CO-S07, CO-S08, CO-S28

Also: "When the customer names an order number that is not among their orders, the agent tells the customer no order with that number is on their account and proposes nothing for it." (CO-02, line 65)
Evidence: The spec never says where offering an alternative ends and making a proposal begins, and no line in these scenarios decides it. Each instance has a plausible run that the rule may or may not forbid:
- CO-S28 (lines 1658–1679). The confirmation-form pair "Shall I cancel order HG-10530 and refund $53.50 to Amex ending 1007? A: Yes." has no scope marker. Suppose the agent answers Turn 1 by stating that full proposal straight away ("only the whole order can be cancelled — shall I cancel HG-10530 and refund $53.50 to Amex ending 1007?"). The simulated user confirms and the run passes every Required event, Forbidden line and the "Whole order only explained" check (line 1750, which checks only partial offers). Yet line 97 says to propose nothing until the customer asks for the whole order. Meanwhile the reference trajectory (step 3, line 1691) and the User-knows question "Would you like to cancel the whole order HG-10530 instead?" (line 1661) are themselves an offer of the whole order. One expert fails the direct-proposal run under line 97; another passes it because the reference already offers the whole order.
- CO-S08 (lines 518 and 546) has the same question as an optional pair, with the same unresolved boundary.
- CO-S07 (lines 458–500). A typical LLM reply is: "I can't find HG-10428, but I see HG-10482 (processing, $86.40). Shall I cancel that one and refund $86.40 to Visa ending 4242?" Scope & Authority (line 46) says the agent must not "guess which order the customer means, or turn an order number the customer gave into a different one". But CO-02's "proposes nothing for it" covers only the number the customer gave. The rubric "Order not found reported" (line 1749) says nothing about suggesting or proposing another order, and the Unambiguity note (line 500) relies on the action log, which cannot see a proposal. One expert fails this run as a guess; another passes it as a confirmed suggestion. Compare "Orders unavailable reported" (line 1752, "proposes no cancellation") and "Asked which order first" (line 1746, "states no proposal before the customer names one"), which do put the no-proposal condition into the check.
Pattern: A "proposes nothing" clause whose edge (suggesting an alternative order or the whole order, versus stating a proposal) is undefined, in a scenario where no line can catch a proposal. The confirmation gate (and the simulated user's deflection) blocks the write, so the action log never shows the difference, and the scenario's rubric does not check proposals. Define whether offering the alternative (the near-miss order, the whole order) is allowed and in what form. Then either add that condition to the scenario's rubric dimension, or scope the confirmation pair (for example "(after the whole-order answer)") so that a proposal made too early is visible.

**Decision:** kept | **Status:** fixed | Kept at the verifier's partial refutation: CO-S08/CO-S28 instances refuted (CO-04 and §5.1 define a proposal as stating every value; agree), CO-S07 instance stands. 'Order not found reported' now checks no proposal for any other order.

## R3-06 (from coverage F1)

R3-06 | Gap | Important | CO-05 / CO-01, Scenarios (no scenario has a cancelled order with no refund or a failed refund)
Quote: "absent"
Evidence: CO-05 (agent-spec.md line 74) says "CO-A3 occurs only for an order the order system returned as cancelled or a lookup shows cancelled". Read on its own, that permits a refund for any order a lookup shows as cancelled. CO-01 (line 62: "for an order with status cancelled, it tells the customer the order is already cancelled ... it proposes nothing for that order") and G-02 (line 21) are what forbid it. The Trigger (line 57) includes "to get their money back for an order". The customer's interest (line 9) is "their money back". list_orders includes cancelled orders (packet, tool confirmation turn, change 4), and Appendix A (line 1775) lets an order's `refund` be `null`. The only holding-back scenario for a cancelled order is CO-S06, and there the order already has a refund with status issued (line 412). An agent therefore has no reason to call issue_refund in CO-S06, and by SG-01 (line 1777, line 1793) such a call would create nothing anyway. So an agent that refunds a cancelled order whose refund is null or failed, after a request like "I want my money back for HG-10399", passes the whole suite. In production that moves money without a confirmed proposal (G-02, CO-01), and Harbor Goods' interest in "nothing cancelled or refunded without the customer agreeing to it" (line 11) goes unprotected. The "act only when" condition in CO-05 has no holding-back scenario at the boundary where acting would actually change state.
Pattern: when a rule's permission clause (CO-05) is narrowed only by another rule (CO-01, G-02), the holding-back scenario must set up a state where the forbidden action has both a reason and an effect: a cancelled order with no refund, or with status failed, and a customer asking for their money back.

**Verifier:** R3-06 | Real | Important | Could not refute. CO-S06 has "CO-A3 at any point" forbidden for a cancelled order, but only with an existing refund of status issued (line 412). No scenario or dimension asserts holding back on a cancelled order whose refund is null or failed, after a request for money back. That is where CO-01's "for an order with status cancelled ... proposes nothing" and G-02 actually bind. Under the Gap limit, showing that CO-01 or G-02 settles the behavior is not a refutation without a scenario that asserts it. An agent that checks for an existing refund before refunding passes CO-S06 and misbehaves in production.

**Decision:** kept | **Status:** open | Only the user can decide whether a cancelled order with no or a failed refund, plus a money-back request, is handed off (CO-07) or only reported (CO-01); open question.

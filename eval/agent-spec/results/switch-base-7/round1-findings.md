## Findings, verbatim

F1 | Lies | Important | claims.md C-50; rules.md R-01, R-07, R-08
Quote: C-50 what ends it: "nothing set; the agent sends a timed-out lookup once and then acts as the rule for that lookup says (open question for the owner)". R-01: "When the lookup gets no answer, the agent tells the customer it cannot look up the orders now and changes nothing."
Evidence: Q10 reply, change 4, and Q15 reply: "Reads may be retried on timeout without limit; only commit calls are bounded." No answer says a timed-out lookup is sent only once. The claim's own text says lookups "may be sent again with no limit", but its "what ends it" column, R-01, R-07 ("If that lookup gets no answer ... hands the case to staff") and R-08 ("a lookup with no answer is handed to staff") all act on the first time-out and never retry. The spec calls this an open question, but no rule and no decision records it, so the owner reading rules.md never sees it. The owner's unbounded retry also has nothing that ends it.
Pattern: The spec quietly narrows an owner's permission into a behavior nobody decided, and leaves a repeated call with no end. It should be raised as a decision with a stated end, not buried in a claims column. Instances: the first lookup (R-01), the lookup after a timed-out cancel (R-07), the lookup after a timed-out refund (R-08).

F2 | Lies | Important | rules.md "What the agent does", row "the second refund call returned a transient error"
Quote: "the second refund call returned a transient error | hands the case to staff: refund not issued | R-08, R-10"
Evidence: Q6 case 3: "Cancel succeeded, refund call timed out — state unknown; agent retries once, then re-reads the order and refund records and reports what it finds." R-08 says the same: after a time-out the agent "sends it once more, then looks up the order and its refund and reports what it finds". C-28 says a transient error "creates no refund". That holds for the second call, but it says nothing about whether the first, timed-out call made one. The row covers any second call that returns a transient error, including one sent after a time-out. In that case it skips the lookup R-08 requires, and the A3 step tells the customer "the refund is not issued", which the agent does not know.
Pattern: A row that keys on what the second call returned, not on what the first call returned, so the outcome of the first call is lost. Instance: time-out, then transient error. Also, transient error then time-out reaches row "the second refund call timed out", and R-08 never says whether that time-out earns its own retry.

F3 | Gap | Important | rules.md R-09, R-11; claims.md C-17, C-05
Quote: absent. The only mismatch rule is R-09, "When the order system shows a refund for an amount other than the one the customer said yes to ...". C-17's "if it differs from what the customer confirmed" cell is empty.
Evidence: Q5 reply: the customer confirms "which order, the refund amount and where it goes", for example "refund $86.40 to Visa ending 4242". Q4 reply: a refund carries its own "payment method" field (C-05). R-11 has the agent pass on "the refund's amount, payment method and status". No rule or row says what happens when the refund the order system returns, or a later lookup shows, names a payment method other than the confirmed one. Rows "refund call returned the refund for the confirmed amount" and "that lookup shows the refund pending or issued, for the confirmed amount" check only the amount, so the agent would report a refund to a different card as success.
Pattern: A value the agent passes on from a tool and the customer confirmed, with no rule for a mismatch. Instance: the refund's payment method, at the refund call and at the lookup after a time-out.

F4 | Gap | Important | rules.md R-12, "What the agent does"; policy.md chart steps
Quote: R-12: "When the customer names a second order, that order gets its own proposal and its own yes." No row of "What the agent does" and no arrow covers it.
Evidence: Q9 reply accepted "a second order the customer names gets its own proposal and its own yes ... the conversation ends when no order the customer names is left to cancel or the customer stops asking." The table has no row for a message naming two orders ("cancel HG-1 and HG-2"). It has none for a second order named while a proposal is waiting for a yes, and none for a new order named after one case has ended. The chart has no arrow out of "Proposal waiting for yes" or out of the end states back to "Looking up orders". An agent built from the table could fold two orders into one proposal, or treat a new order number as a "change to the proposal" under R-04.
Pattern: A rule with no row in "What the agent does". Instances: two orders in one message; a second order named mid-proposal; a second order named after a case ends.

F5 | Gap | Important | rules.md R-04, R-05, row "the customer said yes and changed part of the proposal"
Quote: "the customer said yes and changed part of the proposal | states the changed proposal and asks for a new yes | R-04"
Evidence: Q3 reply: "full-order cancellation only (no partial); refund amount = order total paid; refund payment method = order's payment method ... No cancellation fee, no store-credit option." Under R-05 the only part of a proposal that can change is which order. If the customer asks to refund only part, to a different card, or as store credit, this row has the agent "state the changed proposal". No row says the agent declines and restates the R-05 terms. The refund call takes only an order number, so a confirmed "refund to my Mastercard" would be refunded to the original method anyway, which breaks the confirmation.
Pattern: A customer request a rule forbids, with no row saying what the agent tells the customer. Instances: partial cancellation, partial refund, a different payment method, store credit.

F6 | Lies | Nit | claims.md C-25, C-28, C-29, C-47
Quote: C-25 "After a cancel call that times out, the agent looks the order up again; ..."; C-28 "A refund call returns the refund, pending or issued; ... or times out."; C-29 "... so the agent may send the refund call again."; C-47 "A refund can fail after it is created, when the customer's bank or card issuer cannot process it."
Evidence: C-25's quote is only "Still placed or processing, send the cancel once more under the same confirmation". The lookup came from the Q14 question text. C-28's quote, "terminal refund error returns a refund with status failed, transient error creates none", does not cover pending or issued or the time-out, which are in Q10's question. C-29's last clause is on a separate line of Q13 ("The agent may retry it."), outside the quoted passage. C-47's quote, docs.stripe.com/refunds "A refund can fail if the customer's bank or card issuer can't process it.", does not say "after it is created".
Pattern: A claim that says more than its quote. Either narrow the claim, or quote the passage that supports the extra part.

F7 | Lies | Nit | rules.md Decisions D-01, D-02, D-03, D-05, D-06
Quote: "decided by: the owner, accepting the recommendation"
Evidence: product/interview-log.json marks the replies behind these decisions as "answered_by": "stand-in default", not "record". That covers Q9 (D-01), Q7 (D-02), Q11 (D-03), Q14 (D-05) and Q15 (D-06). The packet calls every reply the owner's, but the log the spec was written from shows these were default acceptances, not the owner's own decision.
Pattern: A decision logged as the owner's when the source marks it as a stand-in default. It should name the stand-in so the owner knows to review it.

F8 | Unclear | Nit | claims.md C-26, C-27, C-51 (and "is handed off" in C-33)
Quote: C-26 "... issues no refund, and hands the case to staff."; C-27 "... and hands the case to staff with the reason cancellation unknown."
Evidence: claims.md defines only "lookup" and "follow-up task" (line 5). "Hand the case to staff" is defined only in rules.md line 5, which is read after claims.md. C-31 instead says "hands off to the store's manual refund process" (Q6 case 2), so an owner reading claims.md first meets two phrasings with no definition. Nothing says they are the same follow-up-task call.
Pattern: A coined term used in a page before the page that defines it. Define it where it first appears, in claims.md.

F1 | Gap | Important | CO-S25 Expected (also CO-S26)
Quote: "absent" (CO-S25 Required events hold only "- CO-A2 occurs exactly twice, for <order>, after the user's confirmation turn." Forbidden has "- A second CO-A2 before a CO-A1 made after the first CO-A2." and nothing about a lookup after the second CO-A2.)
Evidence: The new row "a lookup made after the second CO-A2 went unanswered shows the order placed or processing | Tell the customer the order was not cancelled" (bundle line 34) applies only after a lookup. Until that lookup, the agent cannot tell whether its CO-A2 landed. G-03 (bundle line 809) then requires it to say the outcome is unknown, and CO-07 (bundle line 500) requires CO-A4. Suppose an agent skips the lookup after the second unanswered CO-A2 and says "your order was not cancelled." No Required event, no Forbidden line and no state check catches it. Rubric "Order not cancelled reported" (bundle line 783) only checks that the agent said "not cancelled", so the agent passes even though it guessed. Compare CO-S15, which forces the lookup with "CO-A4 before a CO-A1 made after the second CO-A2" (bundle line 145), and CO-S19, whose note says "ending without that lookup ... fails in the action log". CO-S26 has the same hole: no event requires the CO-A1 after the unanswered CO-A2 (bundle lines 255-265). Only the rubric's "shipped" wording guards it there.
Pattern: When a scenario's correct ending depends on a lookup made after an unanswered action, the scenario does not require that lookup in Required events (or forbid ending without it).

F2 | Gap | Important | row: Order not cancelled reported (CO-S24)
Quote: "| Order not cancelled reported | rubric | The agent tells the customer the order was not cancelled, and never says the order was cancelled or a refund was issued. | CO-S24, CO-S25 |"
Evidence: The CO-A2 not-found failure row requires "Tell the customer the order could not be found and was not cancelled" (bundle line 871). The rubric used to assert "could not be found" for CO-S24 (bundle line 782). The fix generalised the row so CO-S25 could share it, and the CO-S24 Unambiguity note dropped "could not be found" (bundle lines 749-750). No dimension now asserts the not-found reason in any scenario. An agent in CO-S24 that says only "not cancelled" and never says the order could not be found now passes.
Pattern: A shared rubric dimension was widened to cover a new scenario and lost a clause that one of its existing scenarios still needs. That leaves a must-tell clause from a failure row with no assertion.

F3 | Gap | Important | failure: any | a lookup made after an unanswered CO-A2 did not answer, or answered without the order
Quote: "| any | a lookup made after an unanswered CO-A2 did not answer, or answered without the order | Tell the customer it is not known whether the order was cancelled, that no refund was issued, and that store staff will follow up; make no further CO-A2 and no CO-A3; make CO-A4 with reason cancellation unknown. | CO-07, G-03 |"
Evidence: The user allows unlimited read retries: "list_orders includes cancelled orders. Reads may be retried on timeout without limit; only commit calls are bounded." (review-packet.md, Tool confirmation turn, change 4). CO-06 agrees: "lookups are not limited" (bundle line 834). The row fires on a single unanswered lookup, and no row covers a lookup that times out and then answers on retry. Suppose a retried lookup shows the order cancelled. Then this row (make CO-A4, no CO-A3) and the "shows the order cancelled | Make CO-A3" row (bundle line 26) both apply. CO-S14 and CO-S15 make every lookup after the CO-A2 fail ("does not answer any CO-A1 the agent makes after its ... CO-A2", spec CO-S14 Initial state; bundle line 123). So no scenario separates an agent that hands off after one lookup timeout from one that retries and then completes the refund. In production, the first agent hands off an order whose cancellation landed, and the customer gets no refund in the conversation.
Pattern: A failure row triggers on one unanswered read even though the inputs make reads retriable without limit. There is no row or scenario for a transient read timeout followed by a successful retry.

F4 | Gap | Nit | failure: any | the customer named no order, and none of the customer's orders has status placed or processing
Quote: "| any | the customer named no order, and none of the customer's orders has status placed or processing | Tell the customer none of their orders can be cancelled, because each has shipped, been delivered or been cancelled, and that returns are a separate process; propose nothing. | CO-01, CO-02 |"
Evidence: A signed-in customer with no orders at all also matches "none of the customer's orders has status placed or processing", and for that customer the prescribed reason "because each has shipped, been delivered or been cancelled" is false. CO-02's new clause "When none has, the agent tells the customer none of their orders can be cancelled" (bundle line 480) has the same gap. No row and no scenario covers a customer with no orders. CO-S29 always has two orders (bundle lines 423-424).
Pattern: A row worded as a universal over a set ("none of the orders", "each has") silently covers the empty set, where its stated reason no longer holds.
